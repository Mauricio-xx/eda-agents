config.yaml — declaring macros (stage 02)

This is macro integration: the full-chip flow needs a declaration of every hard block sitting on the die — SRAMs shipped with the PDK and any custom block you hardened yourself in stage 01. No placement algorithm runs on these; you pin them.

Part 4 · PDK4 / 5

PDK choice — wafer-space fork, one root for the flow

Both macros and the chip-top point at the wafer-space gf180mcu fork (pinned at tag 1.8.0). The chip-top requires it: the padring instantiates gf180mcu_ws_io__dvdd/dvss, IO cells only the fork ships. The macros use the same root because the standard cell library is not byte-identical between the system PDK and the fork — using one root keeps the cells inside the merged chip-top GDS aligned with the rule deck running DRC + LVS at signoff.

What you type per macro
$ source sak-pdk-script.sh gf180mcuD gf180mcu_fd_sc_mcu7t5v0 $ librelane librelane/counter_macro.yaml \ --pdk gf180mcuD \ --pdk-root <template>/gf180mcu \ --manual-pdk \ --save-views-to build/counter

--manual-pdk disables LibreLane v3 manifest validation (the fork is not in the canonical list); --pdk-root overrides the system path that sak-pdk-script.sh would otherwise resolve. Same pattern for the ALU.

Macros standalone could use the system PDK (verified). Chip-top cannot — the IO cells force the fork. Aligning both on the fork is the safe path the chipathon-2026 reference notebook follows.
